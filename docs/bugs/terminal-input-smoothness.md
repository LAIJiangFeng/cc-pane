# 终端字符与连续拼音输入流畅度

2026-09-13，在 `dev/v0.12.18` 的现有工作树上修复。此记录只覆盖本次输入改动，工作树原有的渲染、尺寸同步和后端修改不计入本次交付。

> 本文记录 09-13 的历史实现。用户随后确认重启整台 Windows 后原 release 也恢复流畅，因此不能将恢复归因于这批 DEV 修改。09-14 已移除 Windows 自定义组合预览、候选字体封装及隐藏输入框几何/透明度覆盖；Windows 输入法按键交给 xterm 自身处理。最终保留与回退范围见 [DEV 输入延迟测量](../diagnostics/terminal-input-latency.md)，不要根据下文重新引入 120ms 预览保留逻辑。

## 发现与修复

1. `terminalService.write` 原先对每个空闲队列的按键固定等待 8ms；即使标记 `flushImmediately`，仍通过 `setTimeout(0)` 发送。普通字符、拼音提交、退格和回车现在直接进入写入链路。已有写入未完成时继续排队、合并连续同源输入，完成后直接接续；不并发写同一个会话，也不让后来的字符越过先前的系统查询回复。非键盘输入仍保留原有的批处理窗口。
2. Windows 选字后的预览保留逻辑没有处理下一轮 `compositionstart`。上一轮的 120ms 定时器或渲染回调会把 xterm 已经激活的新拼音预览隐藏。现在在 xterm 启动新组合前清理旧定时器、动画帧和渲染监听；回调通过代次校验避免影响下一轮。取消组合、失焦和卸载也清理旧状态。
3. 预览保留期间才订阅渲染事件，结束后立即释放；每轮拼音开始时同步当前字体，兼容终端字号调整。

这次移除的是前端排队等待，不代表 PTY 往返、CLI 自身重绘或显示器呈现已经达到原生终端的延迟。

## 现场指标

对 `%LOCALAPPDATA%\com.ccpanes.app\logs\performance` 最近约 15 分钟的记录进行只读汇总：56 个样本，输出排队峰值 0、轮询会话峰值 0、计时器延迟峰值约 14.4ms。采样没有显示当时存在持续输出积压；它不是按键到屏幕的延迟测量，也不能排除短暂卡顿。
